# Go Drift Check

Audit this repo's Go code for drift across four dimensions and report findings — do not silently
fix anything unless the user asks. This is a reporting skill: read code, compare it against a
baseline, and list what has drifted with file:line references and a concrete fix suggestion.

## Scope

skc-go is a **two-module monorepo** with no root `go.mod`. Audit both unless the user names one:

| Module | What it is | Audit emphasis |
|---|---|---|
| `common/` | Published library (`github.com/ygo-skc/skc-go/common/v3`), consumed through the Go proxy by ygo-service *and other repos* | Exported API surface, shared helpers |
| `ygo-service/` | gRPC service over the SKC MySQL database | SQL, handler/repo layering, hot paths |

**Never flag generated code.** `common/ygo/*.pb.go`, `common/health/*.pb.go`, and `common/swift-gen/`
are protoc output, regenerated by `make -C common all`. Excluding them leaves ~2.7k non-generated
LOC. To fix anything in them you change the `.proto` and regenerate — never the `.go`.

`.claude/rules/coding-priorities.md` (linked from CLAUDE.md's Coding priorities section) is this
repo's standard. This skill is only the **audit procedure** for it — the rule says what good looks
like, the skill says how to find where the code drifted from it. **Re-read the rule at the start of
every run:** its `paths:` glob fires on Go *edits*, so a read-only audit cannot assume it is already
loaded, and it may be updated independently of this skill.

For a repo this size, run checks 1–3 directly with `Bash`/`Grep`/`Read` — they read overlapping
files and produce findings that must be deduped against each other, so splitting them across
subagents costs more than it saves, and second-hand `file:line` references can't be trusted without
re-reading the code anyway.

**Exception:** dispatch check 4 (dependency & capability drift) as a background subagent *before*
starting check 1, then collect its result when assembling the report. It's network-bound, reads only
the two `go.mod` files plus release notes, and shares no findings with the other checks.

If the user asks to check only recent work, scope to `git diff <last relevant tag>...HEAD -- <module>/`.

## 1. Idiomatic Go

The **"Idiomatic Go"** section of `.claude/rules/coding-priorities.md` is the authoritative checklist
here — re-read it before judging anything. What follows is how to audit against it, not a second
standard.

Mechanical baseline — note the **per-module** invocation, since `./...` from the repo root matches
nothing:

```bash
gofmt -l common ygo-service          # anything listed is drift
(cd common && go vet ./...)          # any warning is drift
(cd ygo-service && go vet ./...)
```

Targeted checks beyond that baseline:

- **Logging.** gRPC handlers open a flow with `util.NewLogger(ctx, "Flow Name")` and pass the
  returned ctx down; everything below pulls it back with `util.RetrieveLogger(ctx)`. Bare `slog.`
  calls are correct **only** in startup/init paths that have no ctx (`main.go`, `db/connect.go`,
  `api/server.go`, `util/log.go`'s own `init`). A bare `slog.` inside a repo method or handler is
  drift — grep `ygo-service/api ygo-service/db common/client` for `slog\.` and check each hit.
- **Error boundary types.** Three layers, three conventions — a bare `error` crossing any of them
  is drift:
  - `ygo-service/db/*` returns `*status.Status` (built by `handleQueryError` / `handleRowParsingError`).
  - `ygo-service/api/*` handlers return `err.Err()` — nil-safe on a nil `*status.Status`.
  - `common/client/*` returns `*model.APIError`, converted by `rpcErrorToAPIError`.
- **Repository interface ↔ implementation parity.** Every method on a `...Repository` interface in
  `ygo-service/db/` must exist on its `YGO...Repository` struct *and* be reachable through the
  package var wired in `api/server.go:33-38`. A method on one but not the others is drift. (Unlike
  skc-suggestion-engine there is no mocks file to keep in sync — don't look for one.)
- **Cross-module duplication — the highest-value check here.** A helper that exists in `common/util`
  but is hand-rolled inside `ygo-service` is drift, and the divergence is usually silent. Live
  example: `common/util/grpc.go:11` exports `NewServer`, while `ygo-service/api/server.go:72`
  builds its own `grpc.NewServer` with materially different keepalive and timeout values. Report
  which one is authoritative and whether the difference is deliberate.
- **`common/` is first-party source here — read it.** In skc-suggestion-engine this module is a
  vendored dependency that is deliberately not opened. That rule does **not** apply in this repo;
  `common/` is the source of truth and fully in scope for every check.
- **Exported API surface in `common/`.** It publishes to `proxy.golang.org`, where versions are
  immutable. Per the `releasing-a-module` skill, a changed or removed exported symbol forces a
  **major** bump and a `/vN` path change in every importer. Flag any exported signature change since
  the newest `common/v*` tag that hasn't been released as a major:
  `git diff $(git tag --list "common/*" --sort=-v:refname | head -1)...HEAD -- common/`

## 2. SQL query hygiene (this repo does not own the schema)

**`ygo-service` queries the SKC MySQL database, whose DDL lives in another repo.** There is no
`CREATE INDEX` here to read, so you cannot verify an index exists — do not guess at an inventory or
assert one is "missing." Audit **query shape** instead, and phrase index findings as questions for
the schema owner.

The writing-time standard is already stated in `.claude/rules/coding-priorities.md` — its "Let MySQL
do the filtering" bullet and its `ygo-service/` module-specific bullet. This section is the audit
procedure for those, plus the inventory of what's already known.

Enumerate every query first: the `const` query blocks at the top of each `ygo-service/db/*_repo.go`,
plus the `fmt.Sprintf` call that assembles each one. Then check:

1. **Sargability.** A predicate that wraps an indexed column in a function, or leads with a
   wildcard, cannot use an index and forces a scan. Three already exist and are known:
   `DATE_FORMAT(product_release_date, '%m-%d') = ?` (`product_repo.go:57`), `LIKE BINARY` with a
   leading `%` (`card_repo.go:347`), and `ORDER BY RAND()` (`card_repo.go:121`). Report these as
   **pre-existing**, not new. The check is for *newly added* ones — and weigh severity by table size
   and call frequency before recommending anything.
2. **Parameterization.** Values reach queries through `?` placeholders built by
   `variablePlaceholders(n)` and `buildVariableQuerySubjects(...)`. Any **new** `fmt.Sprintf` that
   interpolates a *request-derived* value into SQL text is a finding. Two pre-existing instances
   interpolate `archetypeName` directly: `archetypeInclusionSubQuery` and `archetypeExclusionSubQuery`
   (`card_repo.go:70-83`, used at `card_repo.go:367` and `385`). Note them as pre-existing; flag
   anything new loudly. Interpolating a *column list or placeholder run* (`cardAttributes`,
   `variablePlaceholders`) is the established pattern and is fine.
3. **`FORCE INDEX` hints.** `score_repo.go:29` pins `FORCE INDEX (FORMAT)`. A hint names an index in
   a schema this repo can't see, so an upstream rename or drop breaks it at **runtime, not compile
   time**. Flag new hints, and confirm existing ones are still intentional.
4. **Projection.** Queries select the explicit `cardAttributes` column list rather than `SELECT *`.
   A bare `SELECT *` against a base table is drift. (`a.*` over an already-projected subquery, as in
   `archetypalCardsUsingCardTextQuery`, is fine.)
5. **Row lifecycle.** Every `QueryContext` needs a `defer rows.Close()`, and `rows.Err()` must be
   checked after the scan loop. **Do not compare grep counts** — `card_repo.go` has 7 `QueryContext`
   calls but only 2 direct `rows.Err()` checks, because five route through `parseCardRows`, which
   checks it. Trace each call to whichever helper consumes its rows (`parseCardRows`,
   `parseRowsForProductItems`) before reporting anything.
6. **Single-row reads** use `QueryRowContext`, and `sql.ErrNoRows` must reach `handleQueryError` so
   it maps to `codes.NotFound` rather than `codes.Internal`.
7. **Unbounded result sets.** A query with no `LIMIT` whose result crosses gRPC must fit
   `grpc.MaxSendMsgSize(2<<20)` (`api/server.go:97`). The archetype and effect-search queries return
   whatever matches — worth flagging if a new one could plausibly exceed that.

Report index findings as: `<table> is filtered/sorted on {field(s)} by <method> (<file>:<line>) in a
shape that cannot use an index — confirm coverage with the schema owner.`

## 3. Performance & memory

The **"Performance"** and **"Low memory footprint"** sections of `.claude/rules/coding-priorities.md`
are the checklist — apply them, don't re-derive new rules. Concretely, look for:

- **Slices grown by `append` whose final size is already known** (`len(input)`) but declared without
  a capacity hint. Only flag when the size is *genuinely* knowable — `make([]*ygo.Card, 0)` before a
  row scan is correct, since the row count isn't known until the scan finishes.
- **Scan variables declared inside the row loop.** `parseCardRows` (`card_repo.go:161-165`) hoists
  them above `for rows.Next()` so one set is reused for every row; a new loop that re-declares them
  per iteration is drift.
- **Range-copy of large values — mostly a non-issue here, so don't manufacture findings.** Per the
  rule's memory section, `common/model` is deliberately interface- and pointer-based and the repo
  layer passes `*ygo.Card`; `[]ProductContent` (`common/model/product.go:25`) is the only value-type
  struct slice today. Flag range-by-value only if a new one appears on a hot path.
- **Sequential fan-out that could be concurrent.** `common/util` ships `AtomicWaitGroup[T]` and
  `WorkerPool` for this. Flag independent downstream/DB calls written sequentially — but *not*
  calls where the first gates or fails fast before the second is needed; those are correctly
  sequential.
- **Concurrency contract violations.** `AtomicWaitGroup.Store` must be called **exactly once** or
  `Load` blocks forever (documented at `util/atomic.go:13`). `WorkerPool.Run` closes `tChan` itself
  and waits — a caller that closes it or skips `Run` deadlocks.
- **Per-item downstream calls in a loop** where a batch method exists. `common/client` exposes
  `GetCardsByIDProto` / `GetCardsByNameProto`; a loop calling `GetCardByIDProto` per ID is drift.
- **Pool sizing coherence.** `maxOpenConn = 100` / `maxIdle = 50` (`db/connect.go:19-20`) against
  `grpc.MaxConcurrentStreams(1024)` — flag only if a change makes them contradict each other.

## 4. Dependency & capability drift

Per Scope this should already be running in a background subagent — what follows is that agent's
brief. Run it inline only if no agent was dispatched.

**This is not a version-lag check.** `.github/renovate.json` automerges `minor`, `patch`, `pin`, and
`digest`, so both modules sit on the latest minor/patch by construction — reporting "x.y.z → x.y.z+1"
is noise. The real drift is the opposite: **new capabilities land in `go.mod` and are never adopted.**

Scope to **releases from roughly the last 12 months**. Don't read a dependency's full history.

1. **Internal version drift (check this first — it's unique to this repo).**
   `ygo-service/go.mod` both `require`s `common/v3 vX.Y.Z` *and* declares
   `replace github.com/ygo-skc/skc-go/common/v3 => ../common`. The replace means local builds always
   use the working tree, so **a stale `require` is invisible until something builds without the
   replace.** Compare it against the newest tag:
   ```bash
   git tag --list "common/*" --sort=-v:refname | head -1
   grep "skc-go/common" ygo-service/go.mod
   ```
   If they differ, that's a finding.
2. `go list -m -u all` **per module** — used only to spot an available **major**. Don't build a
   report section from its minor/patch output.
3. For direct dependencies whose API this repo actually exercises — `google.golang.org/grpc`,
   `google.golang.org/protobuf`, `go-sql-driver/mysql` (ygo-service), `testify` (common's only test
   dep) — check release notes over that ~12-month window for additions that map onto something this
   repo does by hand. Grep the module path first so you know which symbols are in use. Skip
   plumbing this repo barely touches directly (`uuid`, `godotenv`, `x/net`, `genproto`).
4. **Go stdlib**, since both modules pin `go 1.26`: check recent Go releases for stdlib or language
   additions that would replace hand-rolled code — e.g. a `slices`/`maps` helper standing in for a
   manual loop in `common/model` or `common/parser`.

**Major version bumps deserve real time.** Renovate does *not* automerge majors, so one may be
sitting in an open PR (`gh pr list` is worth a look). Report what changed, which files import the
module, and roughly what migration involves.

Deprecations count when they affect a symbol this repo imports, but they're secondary — lead with
adoptable additions.

Every finding must tie back to concrete code. "grpc-go added X" is not a finding; "grpc-go added X,
which would replace the hand-rolled Y at `api/server.go:72`" is. If a release window turns up
nothing, say so — a short, empty section 4 is the expected result most runs.

## What NOT to flag

- **Generated protobuf code.** See Scope.
- **Exported `common/` helpers that nothing in this repo calls.** `common` is a published library —
  `WorkerPool` and `AtomicWaitGroup` have zero in-repo callers but are used by downstream repos.
  Unused-in-repo is not dead code here. (Unexported helpers with no callers *are* fair game.)
- **The pre-existing SQL shapes named in section 2.** Report them as pre-existing context if
  relevant; don't re-litigate them as new findings every run.
- **Whatever the rule's closing line rules out** — speculative micro-optimizations that hurt
  readability, and defensive guards for failure modes that can't occur in this environment.

This skill finds drift from the standard `.claude/rules/coding-priorities.md` already states — it is
not license to invent stricter rules. When in doubt, quote the rule line the finding is drifting
from, plus the file:line where the code diverges.

## Report format

Respond directly in the conversation (no file unless the user asks). Group by module where a section
has findings in both:

```
## Go Drift Check — <modules audited>

### 1. Idiomatic Go
- <module>/<file>:<line> — <what drifted> — <fix>
(or: "No drift found.")

### 2. SQL query hygiene
- <table> filtered on {field(s)} by <method> (<file>:<line>) — <shape problem> — <suggested fix / question for schema owner>
(or: "No drift found.")

### 3. Performance & memory
- <module>/<file>:<line> — <what drifted> — <fix>
(or: "No drift found.")

### 4. Dependency & capability drift
- common/v3 require in ygo-service/go.mod is <X> but newest tag is <Y>
- <module/stdlib> added <feature> in <version> — could replace <what> at <file>:<line>
- MAJOR AVAILABLE: <module> <current> → <new major> — <what changed> — <files importing it>
(or: "No adoptable additions found in the last ~12 months.")
```

If the user then asks to fix a finding, treat it as a normal edit and rely on the repo's
`PostToolUse` hook (`.claude/settings.json` — gofmt + vet + test on the changed package, owning
module resolved automatically) rather than re-running the whole audit. If the fix touches an
exported symbol in `common/`, say whether it forces a version bump under the `releasing-a-module`
rules.
